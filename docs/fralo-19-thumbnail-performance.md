# FRALO-19：批量图片缩略图性能

大量图片会增加切换设备后的整批缩略图完成时间。旧实现还会完整渲染已经过时的批次，再丢弃结果；每张结果到达主线程后又重建整个列表。本次取消过时任务、复用有界缓存，并改为单行更新。首次生成仍随图片数量增长，不承诺任意数量瞬时完成。

## 测量

2026-10-31 至 2026-11-01，Apple M2 Max、macOS 27.0.1、Swift 6.4，Debug 构建。基线为 `81861d51128dedb40b121bb2423c1d6a51afac2e`。复制仓库 `03-journal.png` 为独立文件路径，测量真实窗口控制器与实际渲染器；每种数量运行一次，不是统计基准，也不代表不同分辨率、格式或硬盘环境下的保证。

| 图片数 | 操作 | 原实现 | 修正后 |
| --- | --- | ---: | ---: |
| 100 | 首次整批生成 | 1.76 s | 1.72 s |
| 100 | 连续切换手机横屏 → 平板 → 浏览器，等待最终整批 | 4.85 s | 1.58 s |
| 100 | 切回手机竖屏，等待整批 | 1.73 s | 0.16 s |
| 500 | 首次整批生成 | 8.70 s | 9.20 s |
| 500 | 连续三次切换，等待最终整批 | 24.37 s | 8.53 s |
| 500 | 切回手机竖屏，等待整批 | 8.42 s | 8.02 s |

500 张连续切换的等待时间减少约 65%。首次生成没有得到改善；500 张切回时的两套缩略图超过缓存预算，LRU 淘汰造成重新渲染。缓存命中不能作为所有大批次的性能承诺。缩略图后台工作与主画布预览有各自的串行队列，表中是整批完成时间，不是按钮响应时间。

重现命令：

```sh
FRALO_THUMBNAIL_BENCHMARK=1 swift test --build-system native --filter ThumbnailPerformanceTests
FRALO_THUMBNAIL_BENCHMARK=1 FRALO_THUMBNAIL_COUNT=500 swift test --build-system native --filter ThumbnailPerformanceTests
```

测试默认跳过性能测量，以免把硬件耗时当成 CI 阈值。

## 原因与修正

- 旧代码每次切换把整批图片逐张加入串行队列；generation 检查仅阻止旧结果上屏，不阻止旧渲染继续执行。新实现每批一个工作项，在每张渲染前后检查取消令牌，已排队的旧批次取消，至多等待正在执行的一张。
- 旧结果回调做线性查找、映射全部条目、整表 reload 和重新滚动至选中行，整批产生二次方级的主线程数据工作。新实现为条目建立 ID 索引，只更新对应表格行，保留滚动、选中和无关行视图。
- 缓存按输入身份、文件大小/修改时间、当前设备有效形态区分；仅缓存成功结果，按 LRU 控制在 64 MiB 像素成本和 1024 项以内。当前显示的图片、撤销记录与渲染中的内存不包含在缓存预算中，预算不是整个应用的 RSS 上限。
- 手机型号/方向、平板方向、浏览器类型/比例影响缩略图。背景、透明度、阴影、导出选项和非当前设备选项不触发无效重算。保持既有 180 px、无阴影、完全不透明的套框结果。
- 调度时先处理选中图片；追加利用已有缓存。删除、清空与撤销重新协调请求，设备设置的撤销/重做也同步缩略图。
